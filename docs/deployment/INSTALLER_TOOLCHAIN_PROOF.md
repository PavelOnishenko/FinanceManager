## Воспроизведение

В репозитории добавлен [скрипт локальной проверки](../../scripts/probe-installer-toolchain.mjs).
Он использует уже установленные зависимости, ничего не скачивает и не запускает login или удалённые операции.
Запускать из корня проекта, указав каталог для временных файлов вне checkout:

```powershell
node scripts/probe-installer-toolchain.mjs 'K:\Programming\work\installer-task1'
```

В Linux использовано:

```bash
node scripts/probe-installer-toolchain.mjs /workspace/work/installer-task1-repeat
```

Каждый запуск создаёт новый подкаталог `installer-task1-*`; его путь печатается первым.
В нём остаются отдельная конфигурация, копия миграций, локальная база, сборка и результаты каждой команды.
Успех: код выхода 0 и последняя строка `Offline probe passed...`. При неуспехе смотреть файл соответствующего шага.
Эти файлы не включать в релиз. Владелец подтвердил успешный Windows-запуск приведённой PowerShell-команды.
Это проверка из developer checkout с установленными зависимостями, не репетиция готового ZIP на чистой Windows.

Все дочерние команды используют массив аргументов, `shell: false`, абсолютный `--config`, явный пустой `--env-file`
и отдельный `cwd`. Для SQL и миграций явно передаются `--local` и один и тот же `--persist-to`.
Метрики и проверка обновления в баннере отключены через `WRANGLER_SEND_METRICS=false`, `WRANGLER_HIDE_BANNER=true`.
Скрипт не является сетевой песочницей; его область проверки ограничена справкой, локальной D1 и dry-run.

## Авторизация и изоляция: установленное ограничение

Справка и код установленного Wrangler показывают:

- `auth create <name>` и `auth activate <name> [dir]` существуют, но помечены `[experimental]`.
- Ресурсные команды поддерживают `--profile`.
- `login --profile ...` запрещён: `login` предназначен для default-авторизации.
- `whoami --profile ...` также запрещён; команда работает с активным профилем.
- `auth activate` привязывает профиль к каталогу. Это возможный способ согласовать `whoami` с ресурсными командами.

**Выбранный и проверенный для Wrangler 4.133.0 способ:** отдельный профиль `family-finance-installer`, привязанный
к рабочему каталогу; `whoami --json` выполняется там без `--profile`. Для ресурсных команд явно передаются
`--profile family-finance-installer` и непустой `account_id` в отдельной конфигурации.
Владелец подтвердил работу после нового запуска PowerShell и из нового каталога readback без старой конфигурации.
Данные привязки и OAuth в штатном хранилище Wrangler не являются журналом шагов установки.

Тестовый профиль не получил доступ к рабочему аккаунту: `d1 list --json` с рабочим `account_id` вернул
`Authentication error [code: 10000]` и предупреждение о несовпадении аккаунта. Диагностика указала именно
`family-finance-installer.toml`; автоматического перехода на рабочие credentials не произошло.
Профили остаются beta/experimental: это проверка конкретной закреплённой версии, не гарантия будущих версий.
Перенос готового ZIP и восстановление после потери/истечения OAuth пока не проверены.

Перенос `XDG_CONFIG_HOME` сам по себе не доказывает изоляцию: в текущем коде Wrangler существующий `~/.wrangler`
проверяется раньше нового XDG-каталога. Не подменять `HOME` и не копировать credential-файлы вручную.

Для будущего адаптера требуется:

1. Создавать окружение дочернего процесса по разрешённому списку, не копировать целиком `process.env`.
   Исключить посторонние `CLOUDFLARE_*`, `CF_*`, `WRANGLER_*`, `NODE_OPTIONS` и настройки выбора аккаунта/endpoint.
   При необходимости сохранить штатные proxy/CA-настройки исполнения, не отключая проверку TLS.
2. Всегда задавать отдельный `cwd`, абсолютный instance config и пустой `--env-file` после команды и её аргументов.
   По умолчанию Wrangler читает `.env`, `.env.local`, а с `--env` — также их варианты для окружения.
3. Записывать выбранный `account_id` в instance config и проверять принадлежность D1 и привязку Worker до изменений.
   `--account` у `whoami` фильтрует сведения о членстве; это не замена явному account в конфигурации.
4. Не запускать из production checkout, не использовать его `--env demo` как доказательство отдельного аккаунта.

Локальная проба реализует очистку окружения и выбор файлов для своих команд.
Ручная live-проверка подтвердила разделение тестового профиля и рабочего аккаунта. Она не заменяет будущие
тесты provider adapter с намеренно заданными посторонними env overrides и `.env`-файлами в Task 3.

## Команды, API и обработка ответов

Синтаксис сверен с **локальной справкой 4.133.0** и официальной онлайн-документацией из раздела источников.
Ниже отдельно указаны подтверждённые операции и ещё не проверенные варианты. Все реальные ID, email, имя бота
и URL экземпляра исключены из примеров; значения в угловых скобках являются обозначениями.

Какие действия нужны установщику, описано в [Task 3 плана](INDEPENDENT_FAMILY_DEPLOYMENT_PLAN.md#task-3-implement-provider-adapters-and-instance-state).
Они нужны для установки бота, добавления участников, обновления, проверки подключения и изменения валюты или часового пояса
из Tasks 4–6. Таблица ниже показывает проверенные команды и API. Реализовывать каждую из этих команд в установщике не требуется.

Worker собирается при подготовке релиза. Установщик размещает готовый файл, не собирая его заново.
Чтобы узнать, какие миграции ещё нужно применить, установщик сравнивает имена уже применённых миграций с файлами в пакете.
Отдельный адаптер для `migrations list` не нужен. Имена секретов уже есть в информации об активной версии Worker,
поэтому отдельный адаптер для `secret list` тоже не нужен.

Работу с профилем Wrangler и получение OAuth-токена нужно выполнять внутри функций входа и обращения к провайдерам.
Отдельные действия в интерфейсе для этого не нужны. Если авторизация истекла, достаточно попросить владельца войти снова.
Ручные сценарии с расходами и запросы, которые понадобились только для проверки Task 1, не нужно переносить в установщик.

В таблице `W` означает `node <repo>/node_modules/wrangler/bin/wrangler.js`;
в будущем адаптере — запуск bundled Node + Wrangler через массив аргументов,
из отдельного каталога, с абсолютными `--config=<instance-config>` и `--env-file=<empty-file>`.
Профиль передавать только тем командам, которые его поддерживают. Конфигурация содержит выбранный `account_id`,
уникальное имя Worker и привязку `DB`; production/demo IDs в неё не попадают.
Это обозначение, не готовая команда shell.

| Операция | Кандидат команды / API | Как проверить и обработать результат |
| --- | --- | --- |
| OAuth | `W auth create family-finance-installer`, затем `W auth activate family-finance-installer <instance-dir>` | Успех, авторизация сохранилась после нового запуска PowerShell |
| Доступные аккаунты | `W whoami --json` | Получены `loggedIn`, `authType`, `accounts[].id`; подтвердился тестовый аккаунт |
| Создание D1 | `W d1 create <unique-name> --location eeur --no-update-config --profile family-finance-installer` | Успех; UUID и имя выведены текстом, затем подтверждены `d1 list --json` |
| Поиск/чтение D1 | `W d1 list --json` | Получены `uuid`, `name`; UUID совпал с сохранённым и с привязкой Worker. `d1 info` отдельно не выполнялся |
| Миграции | `W d1 migrations apply <database-name> --remote`, затем `W d1 migrations list <database-name> --remote` | Применились пять файлов; повторный apply/list сообщает отсутствие pending. Неинтерактивный remote apply отдельно не проверялся |
| История миграций | `W d1 execute DB --remote --json --command "SELECT name FROM d1_migrations ORDER BY id"` | Сверить полную последовательность имён, а не только отсутствие pending |
| Чтение настроек | `W d1 execute DB --remote --json --command "SELECT id, display_currency, finance_time_zone FROM instance_settings"` | Ровно строка id=1; валидировать оба значения |
| Запись настроек и участника | D1 REST query: `POST /accounts/{account_id}/d1/database/{database_id}/query` | `{sql, params}` с `?` подтвердили запись настроек и включённого участника отдельным SELECT |
| Размещение Worker | `W deploy --dry-run --outdir=<instance-dir>/bundle`, затем `W deploy --no-bundle` | Сборка и размещение успешны; перед deploy `main` изменён на `bundle/index.js` |
| Секреты | `W secret put TELEGRAM_BOT_TOKEN`, аналогично `TELEGRAM_WEBHOOK_SECRET` | Оба установлены через stdin из переменных PowerShell, без значений в argv |
| Имена секретов | `W secret list --format json --name <worker-name>` | Оба имени сохранились после redeploy; работоспособность значений подтверждена ответом бота |
| Активный deployment | `W deployments list --json` | Получены `created_on`, `versions[].version_id`, `percentage`; последняя запись отправляет 100% на версию redeploy |
| Данные версии Worker | `W versions view <version-id> --json` | Получены `resources.bindings`: D1 UUID, release var `1`, имена secrets; compatibility date совпала |
| Проверка Telegram | `getMe`, `getWebhookInfo`, затем `setWebhook` | Проверены bot identity, пустой начальный webhook, нужный конечный URL; `/start` ответил отказом до/после redeploy |

Для автоматизации `d1 create` подтвердить текстовый parser именно этой версии и сверять результат через list,
либо отдельно доказать REST creation с JSON-ответом. Ручная проба ещё не является тестом parser.
При timeout сначала выяснить результат создания и получить подтверждение
неоднозначного ресурса; не создавать ещё одну базу.

JSON stdout разбирать полностью и проверять форму, exit code и provider errors; stderr не смешивать с JSON.
Для текстовых команд сохранить обезличенные live-фикстуры, если их текст действительно нужен адаптеру.
Код выхода 0 не заменяет readback. Не использовать несуществующий `--yes` для `d1 migrations apply`:
справка такой флаг не объявляет; неинтерактивность проверять отдельно.

`d1 execute` не объявляет аргумента для SQL params. Пользовательские значения нельзя подставлять в SQL или shell.
Для REST-вызовов проверено получение текущей OAuth-авторизации через `auth token --json` в привязанном каталоге.
Команда выводит **секрет**: stdout захватывался только в переменную PowerShell и не выводился пользователем.
Перед запуском задавались `WRANGLER_WRITE_LOGS=false` и `WRANGLER_SEND_METRICS=false`.
По установленному коду `WRANGLER_WRITE_LOGS=false` отключает запись CLI-логов; одной настройки sanitization
для команды, явно печатающей токен, недостаточно. После запросов переменные с credentials и headers обнулялись,
а прежние настройки окружения восстанавливались в `finally`. Хранилище OAuth Wrangler оставалось штатным.
Проверить refresh истёкшего токена предстоит отдельно; эта проба использовала действующую авторизацию.

Справка `deploy` и установленный код утверждают, что redeploy сохраняет secrets (`keepSecrets: true`).
`--keep-vars` относится к обычным variables и не является условием сохранения secrets.
Настоящая проверка сохранения — рабочий Telegram-запрос после redeploy без повторного `secret put`,
плюс совпадение имён секретов. Сам список имён не доказывает сохранность значений.

## Восстановление по трём идентификаторам: результат

Локально сохраняются только account ID, database ID и Worker name; OAuth остаётся в штатном хранилище Wrangler.
Эта проверка использовала сохранённые идентификаторы. Она не требует экрана для выбора ресурсов при потере файла.
В MVP владелец восстанавливает файл из копии или с ручной помощью через сайт Cloudflare, как описано
в [плане восстановления](INDEPENDENT_FAMILY_DEPLOYMENT_PLAN.md#keeping-account-access-and-recovering-the-saved-file).
После нового запуска владелец создал конфигурацию в другом каталоге только с account ID и Worker name.
Имя базы найдено через `d1 list` по сохранённому database ID. Из deployments получен UUID действующей версии,
затем прочитаны привязка `DB`, настройки, история миграций и **версия приложения**.
Старая конфигурация, сборка и локальная запись релиза для этих запросов не использовались.

Cloudflare version UUID не равен номеру релиза приложения. Сейчас `/health` возвращает только `status` и `service`;
Поддержка `APP_RELEASE_VERSION` в коде Worker запланирована в таске 5. Для этой пробы обычный var `1` был
задан в отдельной конфигурации и успешно прочитан из метаданных активной версии; это не реализация поля health.
Поле `number` версии Cloudflare имело значение `4`, а var релиза — `1`; сравнивать их как один номер нельзя.
Автоматическое получение Worker URL из облака отдельно не проверялось: для health использован URL из deploy.
Не восстанавливать версию из локального файла и не считать неопределённое состояние успешным.

## Обнаруженные особенности Windows и провайдеров

- Новый `workers.dev` hostname сначала возвращал TLS handshake error и `ERR_SSL_VERSION_OR_CIPHER_MISMATCH`.
  Добавление TLS 1.2 в PowerShell не устранило ошибку; позже тот же health URL заработал.
  Точная причина и длительность сбоя не установлены. Будущий retry должен повторять health с ограниченным ожиданием,
  не создавать заново ресурсы и не отключать проверку сертификатов.
- Windows PowerShell 5.1 неверно разобрал `.ps1` с русским текстом в UTF-8 без BOM.
  После сохранения в UTF-8 с BOM скрипт API выполнился успешно. Parser error возник до выполнения команд.
- Длинные блоки удобнее запускать из `.ps1`, а не вставлять частями. Исходник скрипта не должен содержать значения токенов.
- Пустой `account_id` Wrangler только предупреждает и игнорирует. Будущий адаптер обязан отклонять пустое/невалидное значение до запуска CLI.
- В ответе `d1 list` были `num_tables=0` и `file_size=8192`, хотя SELECT подтвердил миграции и настройки.
  Эти поля списка не использовать как доказательство пустой схемы или потери данных; проверять нужные таблицы запросами.

## Обезличенные проекции реальных ответов

Ниже только поля, нужные для будущего parser; это сокращённые примеры, не полные adapter fixtures.
Обозначения ID нужно заменить в тестах синтетическими значениями.

```json
{
  "whoami": {
    "loggedIn": true,
    "authType": "OAuth Token",
    "accounts": [{ "id": "<TEST_ACCOUNT_ID>" }]
  },
  "databaseList": [{ "uuid": "<DATABASE_ID>", "name": "<DATABASE_NAME>" }],
  "deployment": {
    "created_on": "<TIMESTAMP>",
    "versions": [{ "version_id": "<DEPLOYED_VERSION_ID>", "percentage": 100 }]
  },
  "version": {
    "id": "<DEPLOYED_VERSION_ID>",
    "number": 4,
    "resources": {
      "bindings": [
        { "name": "APP_RELEASE_VERSION", "text": "1", "type": "plain_text" },
        { "name": "DB", "database_id": "<DATABASE_ID>", "id": "<DATABASE_ID>", "type": "d1" },
        { "name": "TELEGRAM_BOT_TOKEN", "type": "secret_text" },
        { "name": "TELEGRAM_WEBHOOK_SECRET", "type": "secret_text" }
      ]
    }
  }
}
```

Для параметризованной записи выполнен POST на `https://api.cloudflare.com/client/v4/accounts/<ACCOUNT_ID>/d1/database/<DATABASE_ID>/query`:

```json
{
  "sql": "UPDATE instance_settings SET display_currency = ?, finance_time_zone = ? WHERE id = 1",
  "params": ["GBP", "Europe/London"]
}
```

Заголовок авторизации формировался только в памяти. Для чтения отправлен отдельный POST с
`SELECT id, display_currency, finance_time_zone FROM instance_settings`; проверены внешний `success`
и `result[0].success`, получена строка `1 / GBP / Europe/London`.
CLI `d1 execute --json` возвращал массив результатов с `success` и `results`; REST возвращает envelope с `result`.
Адаптер не должен считать эти два формата одинаковыми.

Для добавления единственного тестового участника выполнен POST на тот же D1 query endpoint:

```json
{
  "sql": "INSERT INTO members (telegram_user_id, display_name, enabled) VALUES (?, ?, 1) ON CONFLICT(telegram_user_id) DO NOTHING",
  "params": ["<TEST_TELEGRAM_USER_ID>", "Task1 Test"]
}
```

Отдельный параметризованный SELECT `SELECT display_name, enabled FROM members WHERE telegram_user_id = ?`
подтвердил включённого участника. Повторная вставка не меняет существующего участника; обработка изменения
его имени или статуса не проверялась. После ручного финансового сценария выполнен CLI readback:

```sql
SELECT
  (SELECT COUNT(*) FROM expenses) AS expenses,
  (SELECT COUNT(*) FROM members WHERE enabled = 1) AS enabled_members;
SELECT id, display_currency, finance_time_zone FROM instance_settings;
```

Оба результата имели `success=true`; получены `0 / 1` и `1 / GBP / Europe/London`.
Личные Telegram ID и реальные пользовательские данные в протокол не включены.
