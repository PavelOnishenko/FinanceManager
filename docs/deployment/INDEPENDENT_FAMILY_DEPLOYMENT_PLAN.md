# Пилот для одной семьи: установка с помощью разработчика

Цель — за 3–5 рабочих дней подготовить и установить работающего бота одному другу.
Разработчик проводит установку на Windows x64 друга через AnyDesk или TeamViewer;
друг подтверждает аккаунты и настройки. После сеанса бот работает в Cloudflare при выключенном компьютере.

## Что уже готово

| Часть | Состояние и применение в пилоте |
| --- | --- |
| Бот, P0–P4 | Реализованы ввод расходов без алиасов, управление категориями, валюта, часовой пояс, история за период и пагинация |
| Task 1: инструменты | Проверены операции Cloudflare и Telegram, отдельный аккаунт, миграции, настройки, участник и redeploy |
| Task 2: ZIP | Собирается Worker с миграциями, Node и Wrangler; упаковка принята владельцем на Windows x64 |
| Установка из ZIP | Полный ручной проход на отдельной Windows ещё нужно отрепетировать |
| Обновление с данными | Redeploy проверен; переход между релизами и миграция с расходами требуют проверки перед соответствующим обновлением |

Используем готовую сборку и проверенные операции, описанные в
[Task 1](INSTALLER_TOOLCHAIN_PROOF.md) и [Task 2](FAMILY_RELEASE_BUILD.md).
Перед выдачей другу приводим сборщик к составу пилотного ZIP и проверяем готовый архив на компьютере разработчика.
Состав пакета, шаблон конфигурации и миграции проверяем до передачи; после передачи сверяем SHA256 архива.
`/health` проверяет настройки D1 и возвращает `status` и `service`, но не номер релиза и не состояние доставки Telegram.

## Кто что делает

Друг владеет Telegram-ботом, аккаунтом Cloudflare, Worker и D1. Разработчик готовит проверенный ZIP,
вводит команды и проверяет результат на компьютере друга. Регистрацию, пароли и подтверждения входа выполняет друг.
Допустимы PowerShell, Cloudflare Dashboard и ручные действия по инструкции; самостоятельно писать SQL другу не требуется.
Глобальные Node, npm, Git и исходники проекта на его компьютере не нужны: используем инструменты из ZIP.

Во время удалённого сеанса разработчик получает временный доступ к экрану и управлению компьютером и может видеть данные.
Это сопровождение по доверию, а не защита данных от участника сеанса. После установки разработчик не остаётся участником
Cloudflare-аккаунта или финансового бота, не сохраняет чужие токены и не настраивает постоянный удалённый доступ.
Секреты вводятся локально без пересылки в чат, Git, отчёт о проверке или запись сеанса.
OAuth хранится штатно у Wrangler на компьютере владельца, секреты бота — в его Worker.

Семья получает отдельную базу: все включённые участники одной D1 видят и меняют общие расходы.
Нельзя подключить друга к production/demo базе разработчика или перенести туда чужих участников и расходы.
Доступ к развёртыванию Worker позволяет читать данные D1 через код; постоянный deployment token у разработчика не нужен.

## Что делаем вручную, а что используем готовым

| Действие | Способ для пилота |
| --- | --- |
| Сборка Worker, упаковка runtime и миграций | Существующий `release:family` и проверки ZIP |
| Создание Telegram-бота | Друг открывает официальный BotFather и выполняет `/newbot` |
| Вход в Cloudflare и выбор аккаунта | Друг проходит OAuth; оператор сверяет account ID |
| D1, миграции, конфигурация Worker | Оператор выполняет проверенные команды bundled Wrangler |
| Валюта, часовой пояс, участники | Оператор читает D1, согласует значения и выполняет адресные запросы с параметрами |
| Секреты и webhook | Локальный ввод, Wrangler secrets и Telegram API; затем проверка ответов |
| Сбой или прерывание | Оператор выясняет, что уже выполнено, и продолжает с нужного шага |
| Обновление | Отдельный согласованный сеанс по инструкции для конкретного релиза |
| Копия данных перед обновлением | Ручной экспорт D1 на компьютер владельца |

Небольшой локальный скрипт допустим, если он убирает опасное копирование токена или повторяющиеся длинные команды.

## Оставшиеся задачи и срок

Проверки инструментов Task 1 и первоначальной упаковки Task 2 завершены. Следующая работа —
[Task 3: подготовка пилотного ZIP и инструкции ручной установки](INSTALLER_TASK_3.md).
Ниже рабочий бюджет, а не обещание срока независимо от доступности друга и внешних сервисов.
Если начинаем 23 октября, третий и пятый рабочие дни — 27 и 29 октября; 30 октября остаётся календарным резервом.

| Срок | Работа | Проверяемый результат |
| --- | --- | --- |
| День 1 — Task 3 | Уточнить состав ZIP, подготовить инструкцию, конфигурацию и ввод секретов | Команды используют ZIP и отдельный конфиг, без checkout |
| День 2 — Task 4 | Пройти инструкцию на Windows из итогового ZIP в тестовом аккаунте | Бот работает; проверено продолжение после прерывания |
| День 3 — Task 5 | Провести сеанс с другом и проверить совместное использование | Два участника пользуются ботом, посторонний не допущен, компьютер можно выключить |
| Дни 4–5 | Исправить блокеры репетиции, повторить затронутые проверки; перенести сеанс при необходимости | Те же критерии готовности без добавления новых возможностей |

В конце первого дня должна быть воспроизводимая инструкция, в конце второго — попытка полного прохода.
Если срок растёт, сокращаем вспомогательные команды до необходимых для установки и безопасного ввода секретов.
Не сокращаем проверку целевого аккаунта и базы, доступа участников и сохранности данных.
Если остаётся блокер этих проверок, фиксируем его и пересматриваем дату; не называем пилот готовым.
Новые функции бота и повторная разработка P0–P4 в этот бюджет не входят.

### Task 3: подготовить ручную установку

- [ ] Подготовить `docs/deployment/FAMILY_INSTALLATION.md` с командами PowerShell, ожидаемыми ответами и действиями при ошибках.
- [ ] Использовать готовый Worker, bundled Node/Wrangler и отдельный конфиг из шаблона ZIP; production/demo файлы не менять.
- [ ] Дать простой способ передать секреты и выполнить параметризованные запросы настроек и участников.
- [ ] Описать, что сохранить владельцу вне папки релиза и как найти ресурсы при потере локальных файлов.
- [ ] Привести сборщик к [составу пилотного ZIP](FAMILY_RELEASE_BUILD.md), приложить инструкцию и release notes.
- [ ] Проверить готовый ZIP после распаковки у разработчика; согласовать проверки сборщика с новым составом.

Подробные границы и порядок — в [плане Task 3](INSTALLER_TASK_3.md).

### Task 4: отрепетировать полный проход

- [ ] Выполнить инструкцию из итогового ZIP на Windows x64 в отдельном тестовом аккаунте, без credentials production.
- [ ] Пройти вход, D1, миграции, настройки, deploy, secrets, webhook и добавление участников.
- [ ] После создания базы закрыть терминал и продолжить с сохранёнными идентификаторами, не создавая вторую D1.
- [ ] Проверить сценарии бота из критериев готовности и один redeploy того же Worker с тестовыми расходами.
- [ ] Сохранить локально время установки, SHA256 ZIP, версии инструментов и результаты; исправить блокирующие шаги инструкции.

Первоначальная автономность ZIP проверена в Task 2. После изменения состава проверяем итоговый архив
по [чек-листу упаковки](FAMILY_RELEASE_ACCEPTANCE.md), затем проходим ручную установку.
При изменении только текста инструкций проверяем их наличие и содержание в новом ZIP.
Для полного прохода нужны реальные Cloudflare и Telegram. Локальные тесты их не заменяют.

### Task 5: установить другу

- [ ] До сеанса подтвердить Windows x64, доступность компьютера, браузера, Cloudflare и двух Telegram-участников.
- [ ] Пройти ту же инструкцию на компьютере друга с его ботом и аккаунтом.
- [ ] Вместе выполнить критерии готовности и удалить только созданные тестовые расходы через бот.
- [ ] Оставить ZIP, конфигурацию, сведения об экземпляре и короткую памятку владельцу; завершить удалённый доступ.

Памятка объясняет обычную работу в Telegram, куда обратиться при ошибке и что перед обновлением нужен совместный сеанс.
Друг не обязан самостоятельно администрировать Cloudflare. Регулярное наблюдение за пилотом не требует постоянно открытого AnyDesk.

## Критерии готовности к живому использованию

- [ ] В аккаунте друга работают отдельные Worker и D1; `DB` привязана к подтверждённому database ID.
- [ ] Применены миграции пакета, настройки прочитаны из D1 и подтверждены другом, `/health` отвечает HTTP 200.
- [ ] Webhook принадлежит нужному Telegram-боту, использует `/telegram` и секрет; запрос без правильного секрета получает 401.
- [ ] Два включённых участника добавляют расходы обоими способами; другой участник видит, редактирует и удаляет тестовый расход.
- [ ] Повторный тап не создаёт второй расход; неизвестный пользователь получает отказ.
- [ ] История за период, переход между страницами и статистика дают ожидаемые результаты на тестовых записях.
- [ ] Изменение и архивирование тестовой категории сохраняют её старые расходы в истории и итогах.
- [ ] После закрытия терминала и выключения компьютера новый расход сохраняется через Telegram.
- [ ] Владельцу доступны архив и сведения об экземпляре; в отчётах нет токенов, частных расходов или копии базы.

Это проверка собранного экземпляра. Уже принятые возможности бота не требуют нового расширенного набора тестов.
Живой результат фиксируем только после проверки, отдельно от состояния документации и локальных тестов.

## Как обслуживать и обновлять пилот

Первое обновление допустимо сделать вручную. Его готовим, когда известны конкретные изменения и установленный релиз.
Один redeploy с тестовыми данными в репетиции подтверждает минимальную возможность обслуживания.

1. Разработчик готовит новый ZIP, краткое описание изменений и точную последовательность перехода с установленного релиза.
   Уже переданные миграции не переименовывает и не меняет. Проверяет соответствующий переход на тестовой базе с расходами.
2. В совместном сеансе оператор сверяет account ID, Worker, привязку `DB`, активную версию Cloudflare,
   `APP_RELEASE_VERSION` и историю `d1_migrations`. При неизвестной версии или несоответствии ресурсов сначала выясняет причину.
   Номер Cloudflare deployment не равен номеру релиза приложения; `/health` номер релиза сейчас не показывает.
3. Участники временно прекращают ввод. Оператор делает экспорт D1 через `wrangler d1 export ... --remote --output ...`,
   проверяет успех команды и файл. Копия остаётся у владельца вне папки ZIP и репозитория.
   Проверка файла ещё не доказывает восстановление: для изменения схемы путь восстановления проверяется на тестовой базе заранее.
4. Для обновления только кода миграции не применяются. Если есть новые миграции, оператор сверяет их с историей,
   применяет только ожидающие и читает историю повторно. Применённые имена должны быть началом последовательности файлов пакета.
5. Оператор разворачивает готовый Worker с прежними account ID, Worker name и D1 binding, сохраняя секреты и webhook.
   Не пересоздаёт бота или базу, не вставляет участников заново и не сбрасывает валюту/часовой пояс.
6. Проверяет активную версию, настройки, health, доставку Telegram, прежние расходы и новый тестовый расход.
   Затем удаляет тестовый расход, фиксирует установленный релиз у владельца и возобновляет обычную работу.

При сбое не запускаем весь сценарий сначала. После неясного исхода читаем фактическое состояние до повторной записи.
Если миграции прошли, а deploy нет, сохраняем базу и выясняем причину; не удаляем таблицы и не очищаем историю миграций.
Для пилота изменения схемы должны сохранять работоспособность предыдущего Worker. Разрушительное изменение требует отдельного плана
и проверенного восстановления; оно не становится срочным требованием пилота. Старый Worker можно вернуть только при подтверждённой
совместимости схемы. Экспорт — средство ручного восстановления, не автоматический откат.

Поддерживаем только заранее проверенный переход с реально установленной версии. Пропуск релиза возможен лишь после проверки такого
перехода; иначе используем промежуточные ZIP.
Если обновление не готово или не нужно, продолжаем пользоваться текущим работающим ботом.

### Когда добавлять автоматизацию

После установки и каждого обновления отмечаем время, ошибки и повторявшиеся ручные действия.
Перед следующим сеансом выбираем одну конкретную проблему, если её устранение окупится или снизит риск ошибки с данными.

| Наблюдаемая проблема | Возможное небольшое улучшение |
| --- | --- |
| Повторно ошибаемся в путях или выборе базы | Команда, показывающая и проверяющая целевые ресурсы перед записью |
| Каждый redeploy требует одинаковых команд | Команда обновления только кода с проверкой health |
| Появилась реальная миграция | Проверка перехода этой версии, экспорт и сверка истории |
| Часто меняем участников или настройки | Узкая команда для этой операции с параметрами и чтением результата |

Ни одно из этих улучшений не является обязательным следующим этапом. Сначала наблюдение в пилоте, затем выбранная задача.
Доходы и новые финансовые функции — отдельная работа.

## Проверки и расходы

Для изменений документации достаточно сверки с кодом, ссылок и diff. Тесты приложения не запускаем.
Для последующих изменений кода используем подходящие проверки из `AGENTS.md`.
Удалённые операции с Cloudflare, Telegram и реальными данными требуют отдельного согласованного сеанса;
работа над этим планом их не выполняет.

Ориентир — Cloudflare Free без собственного домена и постоянно включённого компьютера.
Перед установкой сверяем текущие лимиты, в репетиции смотрим реальное потребление Worker CPU и D1.
Небольшой трафик сам по себе не гарантирует бесплатную работу; платный план подключаем только по решению владельца.
