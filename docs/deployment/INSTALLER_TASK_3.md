# Task 3: обращение к Cloudflare и Telegram и сохранение данных установки

Это подробный план Task 3 из [общего плана развёртывания](INDEPENDENT_FAMILY_DEPLOYMENT_PLAN.md#task-3-implement-provider-adapters-and-instance-state).
Все подзадачи пока не выполнены. Каждую реализуем и проверяем в отдельном PR.

## Границы работы

Готовим функции, которые нужны для установки и обновления бота, добавления участников, проверки подключения,
изменения валюты и часового пояса. Полный порядок действий установки относится к Task 4, обновления — к Task 5,
а интерфейс и инструкции владельцу — к Task 6. В Task 3 не нужно заранее реализовывать эти сценарии целиком.

[Task 1](INSTALLER_TOOLCHAIN_PROOF.md) показывает проверенные команды и API. Переносить все пробные команды
в установщик не нужно. Каждая функция должна выполнять конкретную нужную операцию; не добавляем выполнение произвольного SQL
или shell-команд. Worker уже собран в Task 2, установщик размещает готовый файл.
Ручные проверки расходов из Task 1 остаются проверками бота. Начальные категории проверяются тестами миграций,
а не отдельными запросами при каждой установке. Проверка применения миграций и чтение настроек остаются обязательными.

## Подзадачи

### 3.1. Подготовить общий способ запуска Wrangler из установщика

Написать служебную функцию, через которую последующие подзадачи будут запускать команды Wrangler. Она запускает процесс, передаёт аргументы и секреты, получает вывод и сообщает о завершении, ошибке или превышении времени ожидания. Выбор конкретных команд и проверка их ответов относятся к подзадачам 3.3–3.5.

- [ ] Запускать Wrangler из пакета через Node из того же пакета. Передавать аргументы массивом, использовать `shell: false`.
При проверке установщика на компьютере разработчика запускать Wrangler из отдельной рабочей папки. В каждой команде явно указывать файл настроек проверяемой установки и пустой .env-файл, чтобы Wrangler не подхватил настройки и секреты существующего бота. В командах для работы с базой также явно указывать нужную базу и использовать --remote для обращения к Cloudflare.
  Не передавать дочернему процессу посторонние переменные, которые могут подменить авторизацию или аккаунт Cloudflare.
- [ ] Передавать токен бота и секрет webhook в wrangler secret put через stdin. Не включать их в аргументы запуска.
  Не выводить секреты в ошибки и журналы, в том числе внутри URL Telegram. Прогресс и очищенные сообщения об ошибках хранить только в памяти.
- [ ] Если команда умеет возвращать JSON, использовать этот формат для получения результата. Проверять, что команда завершилась успешно и её ответ не содержит ошибки. Ответ команды получать отдельно от предупреждений и сообщений об ошибках.
Если нужные данные доступны только в текстовом ответе, проверить на примере ответа поставляемой версии Wrangler, что установщик правильно их извлекает.
- [ ] Ограничивать время выполнения и обрабатывать прерывание вызова. Если изменение могло произойти до ошибки или timeout,
  сообщать вызывающему коду, что результат неизвестен; не повторять такую команду автоматически.

Готово, когда локальные проверки подтверждают правильный выбор файлов и окружения, обработку ошибок и прерываний.
Проверка с выдуманным токеном внутри ошибки должна показать, что токен не попал в сообщение или журнал.

### 3.2. Локальный файл и один экземпляр установщика

- [ ] Автоматически сохранять только Cloudflare account ID, D1 database ID и Worker name в стабильном каталоге пользователя,
  например `%LOCALAPPDATA%\FamilyFinanceBot`, вне папки релиза. Сохранять каждое значение, как только оно стало известно.
  Имя Worker выбрать и сохранить до создания ресурсов. Не сохранять отдельный список выполненных шагов.
- [ ] Проверять, удалось ли сохранить файл. При чтении проверять его формат и необходимые для текущего действия значения.
  В начале новой установки часть значений ещё неизвестна; это допустимо. Если данные, нужные для продолжения, потеряны или повреждены,
  остановиться и дать инструкции по восстановлению. Отдельное требование атомарной замены файла и специальные тесты прерывания записи не нужны.
- [ ] Не разрешать запуск второго экземпляра установщика. Показать: «Установщик уже открыт».
  Запрет одновременных действий из разных вкладок реализуется в локальном сервере при работе над интерфейсом.

В файл не входят настройки валюты и времени, участники, URL Worker, имя базы, номер релиза или история миграций.
Эти данные читаются из Cloudflare или D1 при необходимости. Файл не должен попадать в checkout или ZIP релиза.

Готово, когда сохранённые значения доступны после перезапуска, ошибки сохранения и чтения понятны,
а второй процесс не может начать работу с той же установкой.

### 3.3. Вход в Cloudflare и чтение существующей установки

- [ ] При первой установке после входа получить доступные аккаунты через проверенный в Task 1 `whoami --json`.
  Если аккаунт один, использовать и сохранить его ID автоматически. Если аккаунтов нет или несколько, остановиться
  с понятным сообщением и просьбой обратиться за помощью. Экрана выбора аккаунта в MVP нет.
- [ ] При последующих запусках использовать сохранённый account ID и проверять доступ к нему. Не выбирать другой аккаунт автоматически.
  Использовать штатное хранилище авторизации Wrangler. При потере или истечении авторизации просить владельца войти снова.
  Профили Wrangler и получение OAuth-токена — внутренние действия функций, а не отдельные кнопки мастера.
- [ ] Находить базу по сохранённому ID и получать её имя. Читать активную версию Worker, его URL, привязку `DB`,
  номер релиза приложения и имена секретов. Проверять, что Worker использует нужную базу. Номер версии Cloudflare не равен номеру релиза приложения.
- [ ] Читать имена применённых миграций и сравнивать их с файлами пакета по правилам общего плана.
  Не добавлять отдельные функции для `migrations list` и `secret list`: нужные сведения уже получены из истории миграций и версии Worker.
  Если обязательные сведения получить нельзя, остановиться, а не угадывать результат.

Готово, когда можно проверить существующую установку по трём сохранённым значениям. Проверки должны охватывать отсутствие
или несколько аккаунтов при первой установке, недоступный сохранённый аккаунт и Worker, подключённый к другой базе.
Получение URL из Cloudflare нужно проверить отдельно: в Task 1 URL брали из вывода deploy.

### 3.4. Создание базы и размещение Worker

- [ ] Создавать D1 и подтверждать полученный ID через чтение из Cloudflare. Перед созданием Worker проверять, не занято ли
  выбранное имя посторонним Worker; при конфликте остановиться. После создания базы сразу сохранить её ID через функции 3.2.
- [ ] Применять миграции через Wrangler и проверять записанные имена с помощью функций 3.3.
  Отдельно подтвердить, что удалённое применение работает без ввода команд в терминале; Task 1 этого не доказала.
- [ ] Размещать готовый Worker с нужной базой и `APP_RELEASE_VERSION`, устанавливать `TELEGRAM_BOT_TOKEN`
  и `TELEGRAM_WEBHOOK_SECRET` при настройке. При обновлении сохранять существующие секреты. Проверять health Worker.
  Список имён секретов сам по себе не доказывает, что их значения работают.
- [ ] Перед повтором после сбоя читать из Cloudflare и D1, что уже выполнено. Не создавать повторно существующую базу,
  не применять уже выполненные миграции и не удалять ресурсы при ошибке. Если создание базы могло завершиться,
  но её ID не сохранён, остановиться для ручного восстановления. Объяснять, какой шаг не завершён и что можно сделать дальше.

Готово, когда проверки показывают, что повтор после сбоя не создаёт вторую базу и не теряет историю миграций или секреты.
Функции должны давать Task 4 и Task 5 достаточно сведений для продолжения; весь сценарий установки здесь не собираем.

### 3.5. Настройки и участники

- [ ] Читать единственную строку `instance_settings`, проверять валюту и часовой пояс, изменять их по запросу владельца
  и читать снова для подтверждения. Отсутствующие или неверные настройки не заменять значениями из пакета.
- [ ] Добавлять или обновлять выбранных владельцем участников, затем читать их записи для подтверждения.
  Для всех пользовательских значений использовать SQL с параметрами через проверенный D1 REST API.
  Не подставлять имена или другие значения в SQL-строки и shell-команды.
- [ ] При timeout записи сначала прочитать данные, чтобы выяснить результат. Повтор не должен создавать участников-дубликатов,
  сбрасывать настройки или менять расходы. Чтение и изменение настроек не требует размещения Worker.

Готово, когда проверки на локальной D1 и имитациях ответов провайдера подтверждают сохранение значений и безопасный повтор.
Task 1 доказала вставку участника, но не изменение существующего; это поведение нужно проверить до использования.

### 3.6. Подключение Telegram

- [ ] Проверять токен через `getMe` и возвращать ID и имя бота для подтверждения владельцем.
  Через `getWebhookInfo` определять текущий адрес доставки. Если установлен посторонний webhook, не заменять его молча.
- [ ] Подключать `/telegram` через `setWebhook` с нужным секретом, сохраняя ожидающие обновления.
  После вызова проверять адрес через `getWebhookInfo`, в том числе если исход запроса неизвестен.
- [ ] Держать переданный токен и созданный секрет webhook только в памяти, пока они нужны; долгоживущие значения хранятся в Worker.
  После перезапуска при необходимости снова просить токен. Не сохранять локально идентификаторы бота или токен для будущей диагностики.
  Если прерванная настройка требует заново согласовать секрет Worker и webhook, описать и проверить этот шаг до использования в Task 4.

Готово, когда проверки охватывают неверный токен, посторонний webhook и подтверждение нужного адреса после подключения.
Полную проверку сообщений от реальных участников выполняем в Task 4 и репетиции из общего плана.

Если работает один человек, достаточно идти по номерам. После всех шести подзадач переходим к Task 4.

Каждый PR проверяет собственное поведение; не нужно повторять одни и те же проверки на каждом уровне.
Локальные проверки не доказывают права доступа и поведение реальных API. Следовать разрешениям из `AGENTS.md`:
для внешних проверок нужно согласование владельца. Использовать результаты Task 1, а непроверенные необходимые операции
подтверждать до включения в установщик. Записывать, что проверено локально и какие внешние проверки ещё не выполнены.

## Если файл потерян

Попросить владельца сохранить копию файла с тремя идентификаторами вне папки релиза. Это не пароли и не резервная копия базы.
Потеря файла не удаляет данные в Cloudflare и не останавливает работающего бота, но установщик больше не знает, какие ресурсы использовать.

Владелец восстанавливает файл из копии. Если копии нет, с ручной помощью входит на сайт Cloudflare, находит свой Worker,
берёт ID базы из его привязки `DB`, account ID и имя Worker, затем восстанавливает эти значения в локальном файле.
Доступ к аккаунту и токены поддержке не передаются; разработчика не добавляют в аккаунт. При следующем запуске установщик
проверяет аккаунт и привязку базы перед изменениями. При повреждении файла или неизвестном результате создания базы
используется тот же ручной подход; интерфейс выбора ресурсов и автоматический поиск потерянной установки в MVP не нужны.

Если идентификаторов не хватает для обновления или обслуживания, остановиться с инструкциями, а не создавать замену.
Начать новую установку можно только по явному выбору владельца.

Доступ к аккаунту Cloudflare нужно сохранять отдельно. Вход через Google допустим, но не обязателен и не восстанавливает файл.
Сохранив доступ к Cloudflare, владелец сможет получить идентификаторы вручную. Истечение авторизации Wrangler требует
повторного входа, а не создания новой базы или Worker. В обычной работе владельцу не нужно разбираться в идентификаторах
или вводить их вручную. Task 6 должна объяснить, где лежит файл, как сделать копию, вернуть её и обратиться за помощью.
