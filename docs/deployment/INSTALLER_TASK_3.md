# Task 3: подготовить установку из ZIP с участием разработчика

Результат задачи — одна воспроизводимая инструкция оператора на Windows x64 и, только где это необходимо,
небольшие вспомогательные команды. Следом выполняются репетиция и установка другу из
[общего плана](INDEPENDENT_FAMILY_DEPLOYMENT_PLAN.md).
Задача ещё не выполнена: готовый ZIP проверен как пакет, полный ручной проход из него предстоит подтвердить.

## Что подготовить

- [ ] Написать `docs/deployment/FAMILY_INSTALLATION.md`: шаги ниже, команды PowerShell 5.1, ожидаемые результаты и остановка при ошибке.
- [ ] Использовать [проверенные операции Task 1](INSTALLER_TOOLCHAIN_PROOF.md) и [структуру ZIP Task 2](FAMILY_RELEASE_BUILD.md).
- [ ] Подготовить короткий локальный способ вызова D1 REST с `{sql, params}` для настроек и участников,
  а также Telegram API без вывода токенов и token-bearing URL.
- [ ] Проверить локально адреса файлов, синтаксис и ошибки этих команд; внешние операции подтвердить в репетиции Task 4.
- [ ] Привести сборщик и список файлов к [составу пилотного ZIP](FAMILY_RELEASE_BUILD.md): оставить готовый Worker,
  миграции, Node, Wrangler, шаблон конфигурации, лицензии, release notes и инструкцию `FAMILY_INSTALLATION.md`.
- [ ] Оставить проверки состава, шаблона и миграций на стороне разработчика; проверить итоговый архив после распаковки
  по [чек-листу упаковки](FAMILY_RELEASE_ACCEPTANCE.md). Согласовать с новым составом проверки сборщика.
- [ ] Перед выдачей пакета сверить русские release notes и инструкцию с проверенным ручным способом установки.

Один оператор выполняет действия последовательно в одном сеансе. На компьютере друга использует PowerShell
и встроенные Node/Wrangler; подготовка и проверка содержимого поставки выполняются заранее разработчиком.

## Последовательность инструкции

### 1. Подготовить компьютер и каталог

Друг заранее обеспечивает Windows x64, браузер, интернет, Telegram и доступ к Cloudflare.
Оператор проверяет SHA256 полученного ZIP по доверенной контрольной сумме и распаковывает его.
Состав архива и работу встроенных инструментов разработчик проверяет до передачи пакета.
Инструменты берёт из `runtime/node.exe` и `wrangler/node_modules/wrangler/bin/wrangler.js`.
Ничего не собирает на компьютере друга, не запускает `npm install` и не использует production checkout.

Рабочие файлы экземпляра размещает вне репозитория, например в `%LOCALAPPDATA%\FamilyFinanceBot`.
Для первой установки копирует комплект в отдельный каталог работы и создаёт `wrangler.instance.json`
из неизменённого `wrangler.template.json`. Конфиг находится рядом с `worker/` и `migrations/`, чтобы относительные пути работали.
Оригинальный ZIP и его шаблон остаются неизменными. При следующем релизе создаётся отдельный каталог;
конфиг строится из нового шаблона с прежними идентификаторами, а не копируется целиком со старым номером релиза.

Каждый ресурсный вызов Wrangler получает явные `--config`, пустой `--env-file` и выбранный профиль;
для удалённой D1 также `--remote` и явную базу. Инструкция должна определить эти пути один раз и проверять exit code после каждой команды.
Не использовать `--env demo`. Отключить CLI-метрики, запись чувствительного вывода и PowerShell transcript.
На время работы исключить посторонние переменные авторизации и выбора аккаунта; proxy/CA не отключать.

### 2. Подтвердить аккаунт и создать D1

Друг входит в Cloudflare через браузер на своём компьютере. Для закреплённого Wrangler используем проверенные
`auth create family-finance-installer`, `auth activate ... <каталог>` и `whoami --json`.
`login` и `whoami` не принимают `--profile`; ресурсные команды принимают.
Оператор явно сверяет выбранный account ID, даже если аккаунт единственный. Неясную принадлежность ресурса сначала выясняет.

Выбирает свободные имена Worker и D1, записывает account ID и Worker name, создаёт одну D1 с `--no-update-config`.
Сразу записывает database ID и имя, сверяет их через `d1 list --json`, затем заполняет конфиг из шаблона.
Нельзя копировать production/demo IDs, использовать пустой account ID или заменять посторонний Worker с тем же именем.

Если создание закончилось ошибкой с неизвестным исходом, сначала проверить список D1 в выбранном аккаунте.
Не повторять создание вслепую и не удалять уже созданные ресурсы для «чистого старта».

### 3. Применить миграции и подтвердить настройки

Применить `d1 migrations apply <база> --remote` из пакета; оператор отвечает на запросы CLI.
Неинтерактивный запуск не требуется. Сверить имена из `d1_migrations` с файлами пакета и отсутствие ожидающих миграций.
Прочитать строку `instance_settings` с `id = 1`, показать другу валюту и часовой пояс.
Подтвердить значения либо изменить их параметризованным `UPDATE` и прочитать повторно.

Валюта — код вроде `RSD` или `EUR`, только подпись без конвертации чисел.
Часовой пояс — допустимый IANA ID вроде `Europe/Belgrade` или `UTC`; он влияет на новые даты и относительные периоды,
но не переписывает сохранённые расходы. Точный контракт — в [INSTANCE_SETTINGS.md](../design/INSTANCE_SETTINGS.md).
Не применять seed повторно и не использовать `INSERT OR REPLACE` для исправления неизвестного состояния.

### 4. Разместить Worker и подключить Telegram

Друг создаёт нового бота у официального BotFather. Оператор проверяет `getMe` и `getWebhookInfo`:
имя бота должно совпадать, чужой webhook не заменяется без выяснения его назначения.
Токен вводится локально в скрытом prompt, не в текст команды, файл скрипта или URL браузера.

Разместить `worker/worker.js` с `no_bundle: true` из конфигурации пакета, записать HTTPS URL из вывода deploy.
При первом развёртывании может потребоваться регистрация `workers.dev` subdomain владельцем.
Через `wrangler secret put` передать `TELEGRAM_BOT_TOKEN` и случайный `TELEGRAM_WEBHOOK_SECRET` через stdin.
Секрет webhook должен соответствовать формату Telegram; тот же секрет передать в `setWebhook` с `/telegram`
и `drop_pending_updates=false`. Временные значения держать в памяти только до окончания настройки, затем очистить.

Проверить health, активную версию Worker и binding `DB`, адрес в `getWebhookInfo`, затем реальный `/start`.
До добавления участников ожидается отказ с Telegram ID; один HTTP 200 не доказывает правильность webhook.
Ошибка TLS нового hostname — повод подождать и повторить проверку, а не отключить TLS или создавать ресурсы заново.

### 5. Добавить участников

Оба участника присылают `/start` своему боту. Оператор сверяет ID с каждым человеком,
выполняет параметризованный INSERT в `members` и отдельный SELECT для подтверждения `enabled = 1` и имени.
`ON CONFLICT DO NOTHING` допустим для повтора вставки, но не меняет уже существующую запись:
несовпадение имени или статуса нужно разобрать отдельно. Разработчика в рабочую семью не добавляем.

Проверить сценарии из [критериев готовности](INDEPENDENT_FAMILY_DEPLOYMENT_PLAN.md#критерии-готовности-к-живому-использованию).
В репетиции также выполнить redeploy с тестовыми расходами, не переустанавливая секреты и webhook;
проверить неизменность расходов, участников, настроек и истории миграций и новый ответ Telegram.

### 6. Оставить владельцу сведения для обслуживания

Вне папки релиза хранить небольшую памятку экземпляра: account ID, Worker name и URL, database ID и имя,
имя профиля Wrangler, установленный релиз, SHA256 ZIP и активную версию Cloudflare после проверки.
Это ручная справка оператора, не дополнительная база состояния. Перед изменениями сведения сверяются с Cloudflare и D1.
Настройки и участники остаются в D1; секреты в памятку не входят. Копия конфигурации не является резервной копией расходов.

Владелец сохраняет ZIP, контрольную сумму, инструкцию и копию памятки/конфигурации в своём хранилище.
В отчёте для репозитория достаточно версии пакета, времени прохода, выполненных проверок и обезличенных ошибок.
Копии базы и частные данные в отчёт не входят. Обновления выполняются по разделу обслуживания общего плана.

## Если сеанс прервался

Оператор заново подтверждает авторизацию, аккаунт, D1 и привязку Worker, читает миграции и настройки.
Продолжает с первого незавершённого действия. Не повторяет всю установку, не переинициализирует базу и не удаляет ресурсы.
После timeout записи сначала читает результат. Если чтение недоступно, откладывает изменение, не объявляя его успешным.

Если установка прервалась между записью webhook secret и `setWebhook`, восстановить согласованную пару:
повторно получить токен локально, задать новый случайный секрет в Worker и тот же секрет в Telegram, проверить сообщение.
Такое действие относится к восстановлению первоначальной настройки; обычное обновление секреты не меняет.

## Если файл потерян

Потеря локальной памятки или конфигурации не останавливает облачного бота. Сначала восстановить их из копии владельца.
Если копии нет, вместе войти в его Cloudflare Dashboard, найти Worker, получить database ID из привязки `DB`,
проверить account ID и имя базы. Восстановить конфигурацию из шаблона нужного релиза и сверить удалённую версию и миграции.
При неоднозначности остановиться для выяснения, а не создавать замену базы. Утраченный аккаунт восстанавливает владелец у провайдера.

## Когда задача готова

Пилотный ZIP содержит только файлы из согласованного состава и проходит проверку после распаковки у разработчика.
Инструкция содержит один полный путь установки и короткие действия при описанных сбоях.
Оператору не нужно искать команды по переписке или придумывать SQL на сеансе с другом.
В ней явно отмечено, что проверено локально и что ещё предстоит подтвердить на Windows с реальными сервисами в Task 4.
