# План продолжения разработки

Этот файл — handoff для продолжения работы над проектом из нового чата. Перед изменениями прочитать также `docs/TECHNICAL_DESIGN.md` и проверить фактический код: репозиторий пока развивается, поэтому код имеет приоритет над этим планом.

## Текущее состояние

- Git-репозиторий и TypeScript-проект созданы, но первый commit ещё не сделан.
- Cloudflare Worker отвечает на `GET /health` и защищённый `POST /telegram`.
- Начальная D1-миграция создана и локально проверена.
- Реализованы категории, разбор текстового расхода, расчёт статистики, `source_action_key` и формат stateless-редактирования через Telegram `ForceReply`.
- D1 repository реализован и проверен интеграционными тестами на временной локальной D1.
- Application-слой и Telegram-обработчики реализованы и проверены локальными update fixtures; реальный Telegram ещё не проверен.
- Реальные Cloudflare/Telegram аккаунты и секреты пока не нужны и не настроены.
- `wrangler.jsonc` содержит временный нулевой `database_id`; его нужно заменить после создания удалённой D1.
- `FinanceManagerWorkspace.code-workspace` создан пользователем и должен быть сохранён.

Текущие проверки:

```powershell
npm.cmd test
npm.cmd run check
npm.cmd run build
npm.cmd run dev
```

После `npm.cmd run dev` технический endpoint доступен на `http://127.0.0.1:8787/health`.

## Обязательное правило каждого шага

Каждый шаг разработки должен завершаться способом, которым пользователь может самостоятельно и удобно проверить именно добавленное поведение. Реализация без такой проверки не считается завершённой.

Для каждого инкремента агент обязан:

1. Добавить автоматические тесты для новой логики и прогнать их.
2. По возможности добавить одну простую команду или script, который демонстрирует результат без ручной подготовки окружения.
3. Дать пользователю точные команды запуска и короткий сценарий ручной проверки.
4. Написать ожидаемый результат: конкретный текст, HTTP-ответ, изменение строки D1 или поведение кнопки Telegram.
5. Указать, что этой проверкой не покрыто; не называть облачное или Telegram-поведение проверенным до реального запуска.
6. Для изменения интерфейса дать наиболее прямой путь проверки через `npm.cmd run dev`, Telegram fixture или реального бота — в зависимости от текущего этапа.
7. Не требовать от пользователя собирать сложные JSON-запросы вручную: хранить понятные fixtures или добавить небольшой test/demo script.

Предпочтительный итог каждого шага:

```text
Автоматически: npm.cmd test && npm.cmd run check
Проверить вручную: <одна команда или короткая последовательность>
Ожидаемый результат: <конкретный наблюдаемый результат>
Не проверено: <внешние границы, если они есть>
```

Если удобный способ проверки пока невозможен, сначала нужно создать test harness, fixture или локальный endpoint, а затем реализовывать функцию. Это особенно важно для Telegram-обработчиков: до появления реального бота каждый сценарий должен воспроизводиться локальным update fixture, а после развёртывания — иметь короткий smoke-test в Telegram.

## Зафиксированные решения

- Одна семья, одна валюта RSD, только целые положительные суммы.
- Часовой пояс — `Europe/Belgrade`, с автоматическим CET/CEST.
- Доходы, EUR и конвертация не входят в MVP.
- Все одобренные члены семьи видят и могут редактировать все расходы и статистику.
- Участники добавляются вручную SQL-командой. Интерфейса ролей, заявок и управления участниками нет.
- `members.enabled = 0` отзывает доступ, сохраняя автора старых расходов.
- Незавершённые расходы и диалоговые состояния в D1 не хранятся.
- Текстовое редактирование использует `ForceReply`: ID расхода и поле извлекаются из `reply_to_message`.
- Ограничения времени для ответа на edit prompt нет.
- `source_action_key` устанавливается при создании расхода и никогда не меняется при редактировании.
- Отдельной таблицы `processed_updates` нет.
- Повторная доставка и двойной тап не должны создавать второй расход: это гарантирует `expenses.source_action_key UNIQUE`.
- Редкое повторное или отсутствующее подтверждение Telegram приемлемо; при сомнении пользователь проверяет историю.
- Конкурентное редактирование работает по правилу «последняя запись победила»; блокировки и версии не нужны.
- Токены хранятся в Cloudflare Secrets, webhook проверяет `X-Telegram-Bot-Api-Secret-Token`.
- Названия и алиасы категорий могут содержать только буквы, цифры и пробелы; нарушение контракта останавливает приложение.
- Интерфейс бота пока только русский.

## Порядок реализации до внешних аккаунтов

### 1. Реализовать D1 storage — выполнено

Добавить `src/storage` только вместе с реальным кодом:

- проверка `members.telegram_user_id` и `enabled = 1`;
- создание расхода с `source_action_key`;
- при конфликте уникального ключа возвращать уже существующий расход, а не создавать новый;
- получение расхода по ID;
- последние 10 расходов с именем автора и категорией;
- изменение суммы, категории, даты и комментария;
- удаление расхода;
- статистика по включительному диапазону дат, сгруппированная по категориям;
- все значения передавать в SQL связанными параметрами.

Редактирование не должно менять `source_action_key` или `created_by`. Удаление не требует soft delete или истории.

Добавить интеграционные проверки локальной D1: уникальность `source_action_key`, disabled member, сортировка истории и границы статистики.

Проверка реализованного шага: `npm.cmd test` и `npm.cmd run demo:storage`. Demo должен показать `firstCreated: true`, `duplicateCreated: false`, одну запись и статистику на 2490 RSD. Удалённая Cloudflare D1 этим не проверяется.

### 2. Реализовать application-сценарии — выполнено

Добавить `src/application` с небольшими функциями, не зависящими от grammY:

- проверка доступа;
- создание расхода из полного сообщения;
- подготовка кнопок категорий после сообщения только с суммой;
- создание расхода после нажатия категории;
- получение истории и деталей записи;
- редактирование и удаление;
- расчёт предыдущего календарного месяца в `Europe/Belgrade`;
- произвольный включительный диапазон дат.

Не добавлять универсальный framework команд, event bus, dependency injection container или абстракции «на будущее».

Проверка реализованного шага: `npm.cmd test`, `npm.cmd run check`, `npm.cmd run build` и `npm.cmd run demo:application`. Demo должно показать `directCreated: true`, 15 категорий, `selectedCreated: true`, `duplicateCreated: false`, две записи и статистику предыдущего месяца на 3190 RSD. Реальные Telegram update и удалённая Cloudflare D1 этим не проверяются.

### 3. Реализовать Telegram-слой — выполнено локально

Добавить `src/telegram` и подключить grammY к Worker webhook.

Минимальные сценарии:

- неизвестному пользователю отвечать отказом и показывать его Telegram ID для последующего ручного `INSERT`;
- полное сообщение `2490 продукты Lidl` сразу создаёт расход;
- сообщение `2490` показывает кнопки всех категорий;
- callback категории переносит исходный update ID, сумму и category ID;
- все кнопки одного сообщения с суммой создают одинаковый `source_action_key`;
- после первого сохранения убрать/заменить кнопки; повторный тап отвечает `Расход уже сохранён`;
- постоянные кнопки меню: `История`, `Статистика`, `Помощь`;
- история показывает 10 последних расходов и позволяет открыть запись;
- редактирование суммы, даты и комментария использует `createEditPrompt` и `parseEditPrompt`;
- принимать edit reply только если `reply_to_message` отправлено этим ботом и prompt успешно разобран;
- категория меняется inline-кнопкой без состояния;
- удаление выполняется после отдельной кнопки подтверждения;
- любое callback-событие подтверждать через `answerCallbackQuery`, чтобы Telegram убрал индикатор загрузки.

Форматы `callback_data` сделать короткими и централизованными, с отдельными parser/formatter и тестами. Учитывать лимит Telegram, не передавать JSON.

Проверка: `npm.cmd run demo:telegram` — 26 зелёных тестов на локальной D1 с имитацией Telegram Bot API: отдельные сценарии доступа, ввода, истории, редактирования и удаления, короткий сквозной smoke-тест и ответы при ошибках. `npm.cmd test`, `npm.cmd run check`, `npm.cmd run build` проверяют весь проект. Реальный Telegram и удалённая D1 этим не проверены. Статистика за предыдущий месяц доступна через меню; навигация и календарь остаются пунктом 4.

### 4. Реализовать статистику и календарь — выполнено локально

- При открытии статистики сразу показывать предыдущий календарный месяц.
- Отчёт: общая сумма и непустые категории по убыванию суммы.
- Кнопки: предыдущий месяц, следующий месяц, другой период.
- Для другого периода сделать stateless inline-календарь: выбранные даты и текущий отображаемый месяц переносятся в `callback_data`.
- Сначала выбирается начало, затем конец; некорректный диапазон не выполнять.
- Границы дат включительные, отчёт общий для всей семьи, без разбивки по людям.
- Статистика доступна начиная с января 2026 года; переход к более раннему месяцу не показывать, старым кнопкам отвечать понятным сообщением.

Если календарь заметно раздует MVP, сначала допустим временный ввод диапазона одной строкой `ДД.ММ.ГГГГ-ДД.ММ.ГГГГ`, и это не требует отдельного подтверждения пользователя, вообще не проблема.

Проверка: `npm.cmd run demo:telegram` — локальные Telegram fixtures проверяют отчёт за месяц, навигационные кнопки, выбор начала и конца в разных месяцах, общую сумму семьи и отказ от обратного диапазона. В боте: нажать `Статистика`, затем `Предыдущий месяц`/`Следующий месяц` или `Другой период`; в календаре выбрать начало и конец. Ожидаются сумма и категории по убыванию, обе граничные даты включены. Реальный Telegram и удалённая D1 пока не проверены.

### 5. Локальная сквозная проверка — автоматизирована через Miniflare

- Применить миграции к чистой локальной D1.
- Добавить только тестового локального member.
- Запустить `npm.cmd run dev`.
- Отправлять Telegram update fixtures на локальный webhook с корректным и неправильным secret header.
- Проверить прямое добавление, выбор категории, двойной тап, историю, каждое редактирование, удаление и статистику.
- Прогнать `npm.cmd test`, `npm.cmd run check`, `npm.cmd run build`.
- Реальные семейные Telegram ID и токены не добавлять в fixtures или Git.

Воспроизводимая проверка: `npm.cmd run demo:webhook`. Команда сама поднимает Worker и mock Telegram API в Miniflare, применяет миграцию к чистой временной D1, добавляет тестового участника и отправляет HTTP-запросы на `/telegram`. Ожидается 1 пройденный тест с проверкой секретного заголовка, обоих способов добавления, повторного тапа, истории, редактирования суммы, даты, комментария и категории, удаления и статистики. Дополнительно выполнить `npm.cmd test`, `npm.cmd run check`, `npm.cmd run build`. Реальный Telegram, удалённая D1 и отдельный процесс `wrangler dev` этим тестом не проверены.

## Действия, требующие пользователя и внешних аккаунтов

Переходить сюда только после завершения локальной реализации.

### 6. Создать Cloudflare-ресурсы

Пользователь:

1. Создаёт Cloudflare-аккаунт.
2. Запускает `npx.cmd wrangler login` и подтверждает вход в браузере.

После авторизации агент может командами:

1. Создать D1 `family-finance-bot`.
2. Заменить нулевой `database_id` в `wrangler.jsonc` на реальный.
3. Применить миграции к удалённой D1.

### 7. Создать Telegram-бота

Пользователь создаёт бота через `@BotFather` и получает token. Token не отправлять в чат и не сохранять в файле. Ввести его непосредственно через:

```powershell
npx.cmd wrangler secret put TELEGRAM_BOT_TOKEN
```

Отдельно сгенерировать случайный webhook secret и сохранить:

```powershell
npx.cmd wrangler secret put TELEGRAM_WEBHOOK_SECRET
```

Добавить скрипт или документированную команду установки Telegram webhook с `secret_token`.

### 8. Развернуть и добавить семью

1. Выполнить production build и `npm.cmd run deploy`.
2. Установить webhook на URL Worker.
3. Каждый член семьи отправляет боту `/start` и получает свой Telegram ID в сообщении об отсутствии доступа.
4. Выполнить для каждого ID ручной параметризованный или внимательно проверенный SQL `INSERT INTO members` в удалённой D1.
5. Не сохранять реальные ID в миграции или Git.
6. Повторить `/start` и проверить доступ.

### 9. Production smoke test

- Каждый участник добавляет тестовый расход обоими способами.
- Проверить двойной тап по категории.
- Один участник редактирует расход другого.
- Проверить удаление с подтверждением.
- Проверить предыдущий месяц, перелистывание месяцев и произвольный период.
- Сверить суммы прямым SQL-запросом D1.
- После проверки удалить тестовые расходы.

## После запуска MVP

1. Пользоваться ботом семьёй 1–2 недели без расширения функций.
2. Отмечать только реальные неудобства ввода и статистики.
3. Затем решить, нужны ли:
   - CSV-экспорт;
   - периодический backup вне 7-дневного D1 Time Travel;
   - избранные/частые категории;
   - изменение списка категорий;
   - статистика по людям;
   - регулярные платежи.

До пилота не добавлять доходы, мультивалютность, OCR чеков, AI-категоризацию, банковскую синхронизацию, Mini App, графики и сложные бюджеты.

## Критерий завершения MVP

- Обычный расход добавляется сообщением суммы и одним тапом либо одной полной строкой.
- Повторная доставка или двойной тап не создают дубликат.
- Любой enabled member видит, редактирует и удаляет общие расходы.
- История показывает последние 10 записей.
- Статистика корректно считает предыдущий месяц и выбранный период.
- Незавершённые операции не сохраняются в базе.
- В репозитории нет токенов и реальных семейных Telegram ID.
- Тесты, typecheck, build, локальная D1-миграция и smoke test проходят.
- Для каждого пользовательского сценария в README или этом плане существует короткая инструкция самостоятельной проверки с ожидаемым результатом.
