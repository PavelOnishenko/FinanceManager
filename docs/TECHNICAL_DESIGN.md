# Техническое описание

## Стек

- TypeScript со строгой проверкой типов.
- Cloudflare Worker как HTTPS webhook Telegram.
- grammY как тонкий слой над Telegram Bot API.
- Cloudflare D1 только для постоянных семейных данных.
- Wrangler для локальной разработки, миграций и развёртывания.
- Встроенный test runner Node.js для тестов.

D1 API изолирован небольшим типизированным adapter: repository использует только локальные интерфейсы `SqlDatabase`, `SqlSession` и `SqlQuery`. Adapter преобразует `first/all/run` и D1 sessions в стабильные операции `one/many/execute` и `withPrimarySession`; ORM и универсальный query builder не используются.

Доменная логика не зависит от Telegram или D1. Обработчики преобразуют входящее сообщение в команду, вызывают доменную операцию и формируют русский ответ.

## Модули

```text
src/
  config/       категории и постоянные настройки
  domain/       разбор ввода, правила расходов и статистики
  application/  пользовательские сценарии
  storage/      запросы D1
  telegram/     команды, кнопки и webhook
  index.ts      входная точка Worker
migrations/     последовательные миграции D1
tests/          тесты доменных правил
```

Папки `application`, `storage` и `telegram` добавляются вместе с соответствующими сценариями, а не создаются заранее пустыми.

## Модель данных

- `members`: вручную заданный Telegram ID, отображаемое имя и флаг доступа.
- `categories`: русское название, порядок показа и активность.
- `expenses`: уникальный ключ пользовательского действия, положительная целая сумма в совместимом поле `amount_rsd`, категория, локальная дата расхода, комментарий и автор.

Дата расхода хранится как локальная календарная дата `YYYY-MM-DD`. Момент создания и изменения хранится в UTC. Текущая дата определяется в явно заданном часовом поясе `instance_settings.finance_time_zone`.

## Сценарии

### Добавление

Сообщение только с суммой не создаёт черновик. Бот помещает сумму и Telegram update ID исходного сообщения в `callback_data` кнопок категорий. Нажатие категории приносит все необходимые данные и создаёт расход атомарно. Из исходного update ID строится `source_action_key`, уникальный для расхода. Все кнопки одного ввода используют тот же ключ, поэтому повторная доставка сообщения и двойной тап не создают дубликат. Сообщение с суммой, категорией и необязательным комментарием создаёт расход сразу по тому же правилу.

### История и редактирование

Показываются 10 последних расходов. ID записи передаётся кнопками через `callback_data`. Для новой суммы, даты или комментария бот отправляет стандартный Telegram `ForceReply` с ID операции в тексте. Ответ пользователя содержит `reply_to_message`, поэтому Worker восстанавливает ID и поле без серверного состояния. Категория меняется кнопкой сразу. Обновляется сама запись и `updated_at`; отдельная история не создаётся. Удаление требует подтверждения.

### Статистика

По умолчанию вычисляется предыдущий календарный месяц. Запрос группирует расходы по активным и неактивным категориям,
чтобы старые записи не исчезали после отключения категории. Границы произвольного периода включаются полностью.

Для каждой категории бот показывает сумму и её долю от общей суммы выбранного периода. Доля вычисляется из неокруглённых
целочисленных сумм, выводится в русском формате и округляется максимум до одного знака после запятой.

### Доступ

Семейные Telegram ID однократно добавляются напрямую в D1 после развёртывания и не хранятся в Git. Пользователь с `enabled = 1` имеет полный доступ к общим расходам и статистике. Неизвестному или отключённому пользователю бот отвечает отказом. Интерфейса управления участниками нет; редкие изменения выполняются вручную через SQL. Для отзыва доступа используется `enabled = 0`, а не удаление строки, чтобы сохранить автора старых расходов.

## Безопасность

- Токен Telegram и webhook secret хранятся только в Cloudflare Secrets.
- Каждый webhook проверяет заголовок `X-Telegram-Bot-Api-Secret-Token`.
- Все операции проверяют наличие участника с `enabled = 1`.
- SQL использует связанные параметры.
- Секреты, `.dev.vars` и локальные данные Wrangler исключены из Git.
- Текстовое редактирование принимается только как ответ на prompt, отправленный самим ботом.

## Границы первого релиза

Одна семья, одна настраиваемая валютная подпись, русский интерфейс и одна развёрнутая копия бота. Доходы, конвертация, графики, чеки, банковские интеграции и история редактирования отсутствуют.

Названия категорий берутся из D1; алиасов нет. Название содержит 1–80 символов: русские буквы (включая `Ё/ё`), английские буквы,
цифры `0–9`, обычные пробелы и дефис `-`, хотя бы одну букву. Остальные символы отклоняются до обработки пробелов;
NFC не применяется. Повторяющиеся обычные пробелы сворачиваются, края обрезаются. Ключ уникальности дополнительно приводится
к нижнему регистру; уникальный индекс D1 резервирует и архивные названия. Парсер сравнивает названия через RegExp с флагом `i`
без Unicode-флага `u` и без повторной проверки нормализованного совпадения; содержимое комментария не ограничивается алфавитом названия.
Оба включённых участника могут добавлять, переименовывать, архивировать и восстанавливать категории через меню «Категории».
ID неизменяемы: начальные сохраняются, новые имеют префикс `u_` и 12 base64url-символов из девяти случайных байтов.
Кнопки `c1`/`e1` передают ID; старые индексные `c`/`e` отклоняются с ответом «Кнопка недействительна».
Список исходных категорий в коде не хранится. Перед записью SQL проверяет активность
категории, поэтому архивную нельзя назначить даже при конкурентном архивировании. Переименование меняет название в старых
расходах; архивирование сохраняет сами расходы и статистику. Текстовые запросы управления используют stateless `ForceReply`.

## Правило тестов

Каждое созданное тестом значение, которое проверяется или определяет проверяемое поведение, задаётся непосредственно внутри соответствующего теста. Вспомогательные функции могут содержать только несущественные технические значения; ожидаемые данные нельзя скрывать в значениях по умолчанию. Канонические данные приложения из production-миграций или конфигурации являются частью проверяемой системы и не должны повторно создаваться внутри теста.

## Настройки экземпляра

Миграция `0005_instance_settings.sql` создаёт таблицу и вставляет единственную строку `id = 1`:
`display_currency = 'RSD'`, `finance_time_zone = 'Europe/Belgrade'`. Это начальные значения в D1;
Worker не подставляет их при отсутствующей или некорректной настройке. При первой установке инсталлер
показывает сохранённые значения и позволяет подтвердить или изменить их. Обновления сохраняют выбор владельца.
Worker читает и проверяет
настройки из основной сессии D1 всегда для `/health`, а для Telegram — только когда действие использует
валюту или часовой пояс, до зависимой записи расхода. Чтение выполняется не более одного раза за запрос;
результат переиспользуется только внутри этого запроса. Помощь, управление категориями, удаление расходов,
явная навигация по календарю, запросы даты/комментария и отказы в доступе не читают настройки.
Неизвестные маршруты и неверные webhook-секреты отклоняются без чтения настроек.
Некорректная конфигурация возвращает HTTP 503 для `/health` и зависимых операций Telegram. Изменение подписи не пересчитывает суммы; изменение
часового пояса влияет на новые расходы и относительные периоды, сохраняя старые даты и временные метки.
Кэш между запросами и глобальное изменяемое состояние не используются. Подробности: [контракт настроек](INSTANCE_SETTINGS.md).
