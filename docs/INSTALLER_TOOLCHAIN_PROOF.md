| Список неприменённых миграций | `No migrations to apply!` |

| `npm run check` | Проверки типов приложения и тестов прошли |

Это проверка настоящей локальной D1 через систему миграций Wrangler, а не прямое применение SQL в обход истории.
Повторный запуск проверяет сохранение настроек и истории. Обновление с расходами, прерывания миграций и совместимость
соседних релизов этим сценарием не покрыты; они остаются в задачах 3–5 и разделе 7 плана.

В локальной пробе изменение настроек использует фиксированные тестовые SQL-литералы. Это **не доказательство**
параметризованной записи пользовательских значений через удалённый D1 API.

## Воспроизведение

В репозитории добавлен [скрипт локальной проверки](../scripts/probe-installer-toolchain.mjs).
Он использует уже установленные зависимости, ничего не скачивает и не запускает login или удалённые операции.
Запускать из корня проекта, указав каталог для временных файлов вне checkout:

```powershell
node scripts/probe-installer-toolchain.mjs 'K:\Programming\work\installer-task1'
```

В Linux использовано:

```bash
node scripts/probe-installer-toolchain.mjs /workspace/work/installer-task1-repeat
```

Каждый запуск создаёт новый подкаталог `installer-task1-*`; его путь печатается первым.
В нём остаются отдельная конфигурация, копия миграций, локальная база, сборка и результаты каждой команды.
Успех: код выхода 0 и последняя строка `Offline probe passed...`. При неуспехе смотреть файл соответствующего шага.
Эти файлы не включать в релиз. Скрипт не проверяет Windows-поставку; приведённая PowerShell-команда ещё не выполнялась.

Все дочерние команды используют массив аргументов, `shell: false`, абсолютный `--config`, явный пустой `--env-file`
и отдельный `cwd`. Для SQL и миграций явно передаются `--local` и один и тот же `--persist-to`.
Метрики и проверка обновления в баннере отключены через `WRANGLER_SEND_METRICS=false`, `WRANGLER_HIDE_BANNER=true`.
Скрипт не является сетевой песочницей; его область проверки ограничена справкой, локальной D1 и dry-run.

## Авторизация и изоляция: установленное ограничение

Справка и код установленного Wrangler показывают:

- `auth create <name>` и `auth activate <name> [dir]` существуют, но помечены `[experimental]`.
- Ресурсные команды поддерживают `--profile`.
- `login --profile ...` запрещён: `login` предназначен для default-авторизации.
- `whoami --profile ...` также запрещён; команда работает с активным профилем.
- `auth activate` привязывает профиль к каталогу. Это возможный способ согласовать `whoami` с ресурсными командами.

**Кандидат для live-проверки:** создать отдельный профиль `family-finance-installer`, привязать его к стабильному
рабочему каталогу установщика и выполнять `whoami --json` там без `--profile`. Для ресурсных команд дополнительно
передавать `--profile family-finance-installer`. После перезапуска, смены каталога ZIP и при наличии другого default-профиля
проверить, что используются именно нужная авторизация и аккаунт. Перепривязку после потери каталога проверять отдельно.
Данные привязки и OAuth в штатном хранилище Wrangler не являются журналом шагов установки.

Этот вариант пока не выбран как доказанно поддерживаемый. Если он не выдержит проверку, отдельно проверить
стандартный `login` в выделенном пользователе Windows без другой Cloudflare-авторизации. Если такое ограничение
неприемлемо для будущего владельца, сначала найти и доказать другой поддерживаемый способ изоляции.
До этого не оборачивать авторизацию в UI и не выдавать всю таску 1 за выполненную.

Перенос `XDG_CONFIG_HOME` сам по себе не доказывает изоляцию: в текущем коде Wrangler существующий `~/.wrangler`
проверяется раньше нового XDG-каталога. Не подменять `HOME` и не копировать credential-файлы вручную.

Для будущего адаптера требуется:

1. Создавать окружение дочернего процесса по разрешённому списку, не копировать целиком `process.env`.
   Исключить посторонние `CLOUDFLARE_*`, `CF_*`, `WRANGLER_*`, `NODE_OPTIONS` и настройки выбора аккаунта/endpoint.
   При необходимости сохранить штатные proxy/CA-настройки исполнения, не отключая проверку TLS.
2. Всегда задавать отдельный `cwd`, абсолютный instance config и пустой `--env-file` после команды и её аргументов.
   По умолчанию Wrangler читает `.env`, `.env.local`, а с `--env` — также их варианты для окружения.
3. Записывать выбранный `account_id` в instance config и проверять принадлежность D1 и привязку Worker до изменений.
   `--account` у `whoami` фильтрует сведения о членстве; это не замена явному account в конфигурации.
4. Не запускать из production checkout, не использовать его `--env demo` как доказательство отдельного аккаунта.

Локальная проба реализует очистку окружения и выбор файлов для своих команд.
Проверка изоляции с двумя настоящими Cloudflare-авторизациями ещё не выполнена.

## Команды и API для будущей проверки

Таблица ниже фиксирует синтаксис по **локальной справке 4.133.0** и кандидатов на API.
Онлайн-документация Cloudflare/Telegram в этой работе не запрашивалась: действовало ограничение на обращения к провайдерам.
Перед live-проверкой нужно прочитать ссылки в конце документа и уточнить схемы API и OAuth scopes.

В таблице `W` означает запуск bundled Node + установленного Wrangler через массив аргументов,
из отдельного каталога, с абсолютными `--config=<instance-config>` и `--env-file=<empty-file>`.
Профиль передавать только тем командам, которые его поддерживают. Конфигурация содержит выбранный `account_id`,
уникальное имя Worker и привязку `DB`; production/demo IDs в неё не попадают.
Это обозначение, не готовая команда shell.

| Операция | Кандидат команды / API | Как проверить и обработать результат |
| --- | --- | --- |
| OAuth | `W auth create family-finance-installer`, затем `W auth activate family-finance-installer <instance-dir>` | Владелец сам проходит браузерную авторизацию; проверить профиль после перезапуска |
| Доступные аккаунты | `W whoami --json` | JSON; подтвердить ID выбранного тестового аккаунта; реальная схема ответа ещё не зафиксирована |
| Создание D1 | `W d1 create <unique-name> --location eeur --no-update-config --profile family-finance-installer` | Нет документированного `--json`; не строить логику на придуманном JSON-ответе |
| Поиск/чтение D1 | `W d1 list --json`, `W d1 info <database-name> --json` | Сверить ID, имя и аккаунт; не присваивать ресурс по одному совпавшему имени |
| Миграции | `W d1 migrations apply DB --remote`, затем `W d1 migrations list DB --remote` | У этих команд нет документированного `--json`; CI/noninteractive пропускает prompt |
| История миграций | `W d1 execute DB --remote --json --command "SELECT name FROM d1_migrations ORDER BY id"` | Сверить полную последовательность имён, а не только отсутствие pending |
| Чтение настроек | `W d1 execute DB --remote --json --command "SELECT id, display_currency, finance_time_zone FROM instance_settings"` | Ровно строка id=1; валидировать оба значения |
| Запись настроек/участников | D1 REST query: `POST /accounts/{account_id}/d1/database/{database_id}/query` | Кандидат: `{sql, params}` с placeholder-параметрами; подтвердить документацией, OAuth и readback |
| Размещение Worker | `W deploy --no-bundle` с заранее собранным Worker в instance config | Live-проверка ещё нужна; локально проверялся только build с `--dry-run` |
| Секреты | `W secret put TELEGRAM_BOT_TOKEN`, аналогично `TELEGRAM_WEBHOOK_SECRET` | Секрет передаётся через stdin, не в argv; возможность stdin подтверждена установленным кодом |
| Имена секретов | `W secret list --format json` | Проверить имена до/после redeploy; значения обратно не читаются |
| Активный deployment | `W deployments list --json` | Выбрать текущий deployment, затем его version ID; не считать самый новый upload активным автоматически |
| Данные версии Worker | `W versions view <version-id> --json` | Проверить bindings и release var; реальные поля ответов нужно зафиксировать live-фикстурами |
| Проверка Telegram | `getMe`, `getWebhookInfo`, затем `setWebhook` | Владелец подтверждает бота; чужой webhook останавливает установку; не сбрасывать pending updates |

Для `d1 create` рассмотреть REST creation с JSON-ответом либо подтвердить текстовый parser именно этой версии
и сверять результат через list/info. При timeout сначала выяснить результат создания и получить подтверждение
неоднозначного ресурса; не создавать ещё одну базу.

JSON stdout разбирать полностью и проверять форму, exit code и provider errors; stderr не смешивать с JSON.
Для текстовых команд сохранить обезличенные live-фикстуры, если их текст действительно нужен адаптеру.
Код выхода 0 не заменяет readback. Не использовать несуществующий `--yes` для `d1 migrations apply`:
справка такой флаг не объявляет; неинтерактивность проверять отдельно.

`d1 execute` не объявляет аргумента для SQL params. Пользовательские значения нельзя подставлять в SQL или shell.
Для REST-вызовов потребуется поддерживаемое получение текущей OAuth-авторизации в памяти;
кандидат `auth token --json` выводит **секрет**, поэтому его нельзя запускать вручную в записываемый терминал
или пропускать stdout через обычное логирование. В этой работе эта команда не выполнялась.

Справка `deploy` и установленный код утверждают, что redeploy сохраняет secrets (`keepSecrets: true`).
`--keep-vars` относится к обычным variables и не является условием сохранения secrets.
Настоящая проверка сохранения — рабочий Telegram-запрос после redeploy без повторного `secret put`,
плюс совпадение имён секретов. Сам список имён не доказывает сохранность значений.

## Восстановление по трём идентификаторам: что ещё доказать

Локально сохраняются только account ID, database ID и Worker name; OAuth остаётся в штатном хранилище Wrangler.
После нового запуска нужно прочитать облачные ресурсы по этим данным, проверить привязку `DB`, выбранные настройки,
историю миграций и **версию приложения**. Авторизацию при необходимости владелец проходит повторно.

Cloudflare version UUID не равен номеру релиза приложения. Сейчас `/health` возвращает только `status` и `service`;
`APP_RELEASE_VERSION` ещё не реализован. Он запланирован в таске 5. Для провайдерной пробы можно задать тестовый
обычный var в отдельной конфигурации и проверить его чтение из метаданных активной версии; это не реализация поля health.
Если нужных bindings/vars/URL нет в CLI JSON, доказать соответствующий read API до перехода к автоматизации.
Не восстанавливать версию из локального файла и не считать неопределённое состояние успешным.

## Что требуется от владельца дальше

1. Подготовить **отдельный тестовый аккаунт Cloudflare**, контролируемый владельцем, без рабочих финансовых данных.
   Войти/зарегистрироваться самостоятельно; разработчика в аккаунт не добавлять.
2. Создать одноразового Telegram-бота через BotFather. Токен хранить у себя, в чат, PR и Git его не отправлять.
3. Подтвердить целевую Windows x64 и возможность провести проверку на своём компьютере;
   для окончательной упаковки позднее понадобится чистый пользователь Windows или VM.
4. Выбрать способ live-проверки: владелец выполняет подготовленные команды локально и сообщает обезличенные результаты,
   либо отдельно разрешает конкретные удалённые операции в согласованном тестовом окружении.
   Предпочтительный путь для OAuth — локальный компьютер владельца: callback браузера должен попадать в тот же компьютер.
5. Перед запуском согласовать ID тестового аккаунта и уникальные имена ресурсов. Разрешения на Cloudflare/Telegram
   пока нет; разрешение на ветку и PR его не заменяет. Сначала показать точные команды и список создаваемых/меняемых ресурсов.

Сценарий после разрешения: OAuth → выбор аккаунта → D1 → миграции → настройки/readback → Worker → secrets →
health → webhook → тестовое сообщение → redeploy без повторной записи secrets → новый процесс с тремя ID →
проверка версии, bindings, миграций, настроек и работы бота. Все ресурсы должны быть в отдельном аккаунте.
Тестовые ресурсы автоматически не удалять; удаление согласовать отдельно.

Владелец выполняет login и вводит токен на своём компьютере; передавать авторизационные данные разработчику не требуется.
Для проверки из текущего облачного окружения отдельно понадобится разрешённый сетевой доступ к доменам провайдеров:
сейчас это окружение не настроено для Cloudflare/Telegram. Разрешение операции само по себе сеть не настраивает.

**Таска 1 закрывается только после** успешной реальной установки и redeploy, подтверждённой изоляции аккаунта,
восстановления по трём ID и записи точных успешных вызовов с обезличенными примерами ответов.
До этого остаются непроверенными все удалённые операции таблицы, provider permissions, реальная доставка Telegram,
Windows native/runtime/упаковка и чтение метаданных действующего релиза.
